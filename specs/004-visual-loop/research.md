# 阶段 0 调研：视觉 Agent 闭环

**日期**: 2026-09-18 | **关联计划**: [plan.md](plan.md)

## 决策 1：ffmpeg 与帧解码依赖

**决策**: 新增 `numpy` + `imageio` + `imageio-ffmpeg` 三个依赖。imageio-ffmpeg 的 wheel
自带 ffmpeg 二进制，免系统安装；ffprobe 探测与帧解码都走它。

**理由**: 视觉评估器必须读真实视频文件；系统级 ffmpeg 在 WSL/CI 都要额外安装步骤，
wheel 内嵌二进制最省心且版本可锁定（uv.lock）——可复现性即确定性（原则一）。

**已评估的替代方案**: 系统 apt 安装 ffmpeg（环境漂移，CI 多一步，被否）；PyAV
（编译链更重）；OpenCV（大型依赖，功能远超所需）。

## 决策 2：模拟生成器 = 参数哈希种子 + 程序化帧

**决策**: `SimulatedVideoGen` 以 `blake3(规范化生成参数)` 为种子，用 numpy 程序化生成
帧序列（渐变/纹理/运动块等确定图案，种子派生参数控制亮度、色彩、运动幅度、噪声），
经 imageio-ffmpeg 编码为 mp4。同参数产出**逐字节相同**的文件。

**理由**: 闭环开发与 CI 需要"像真的但可复现"的生成器；逐字节一致使工件哈希稳定，
内容寻址与重算一致性测试才可断言。图案参数覆盖评估器的观测维度（亮度→闪烁、
纹理→美学、主体块→一致性），让五评估器都能产生有区分度的分数。

**已评估的替代方案**: 随机噪声帧（评估器无区分度，被否）；预录视频文件进仓库
（二进制入库，被否）。

## 决策 3：帧采样规则确定性

**决策**: `frames.py` 固定采样规则：等间隔取 N=8 帧（含首尾），缩放至 64×64 灰度 +
保留 RGB 缩略图；采样参数（N、尺寸、色彩处理）序列化进评估器版本元信息。

**理由**: 采样是评估器的输入边界——采样规则变了结果就变，必须纳入版本冻结
（原则一）。固定规则 + 固定解码后端（决策 1）= 输入可复现。

## 决策 4：启发式评估器的确定性设计

**决策**: 三个 proxy 与 rule 评估器全部纯 numpy 计算：
- `format_compliance`：ffprobe JSON 对照 configs 规格（分辨率/时长/帧率/编码）；
- `aesthetic`：帧统计合成（亮度分布、色彩丰富度、对比度、Laplacian 锐度）加权映射；
- `identity_consistency`：每帧感知哈希（64 位 dhash）作嵌入，跨镜头余弦距离均值映射，
  单镜头返回 1.0 并注明（规格边界情况）；
- `flicker`：相邻帧亮度直方图差的方差 + 高频伪影能量，反向映射（越稳越高分）。
版本号 = `1.0.0+<实现文件与采样参数哈希前12位>`；得分一律经 `quantize` 定点归一。

**理由**: 真实模型（美学评分网络/人脸嵌入）需要权重文件与推理框架，一期不接
（规格假设）；启发式实现满足确定性、零凭证、可测试三约束，且版本号如实标注
"这是启发式实现"（原则六：不假装是真实模型）。

## 决策 5：judge 委员会 = 3 固定提示词 × 锚点集成对比较

**决策**: `judge.cinematic` 以 configs 中冻结的锚点片段集为参照：候选片段与每个锚点
做 3 个固定提示词的成对比较（经 LLM 网关，Mock 后端哈希种子确定性投票），胜率均值
映射 [0,1]。提示词文本与锚点集哈希进入评估器版本号——变更即新版本（SC-007 可机检）。

**理由**: dev doc §2.3 明确"3 提示词成对比较投票"；成对比较需要参照物，冻结锚点集
是参照物的诚实来源。单点打分会引入评分尺度漂移，成对胜率天然归一。

**已评估的替代方案**: 候选间两两 round-robin（成本随候选数平方增长且引入候选间耦合）；
单点打分（尺度漂移）。

## 决策 6：得分定点归一

**决策**: 新增 `core/evaluators/quantize.py`：`quantize_score(x) -> float` 统一保留
6 位小数（round-half-even），所有评估器得分入库前必须经过它。

**理由**: 浮点计算的 min/max 归一在不同路径可能产生末位差异（如并行归约顺序），
定点归一使"重算逐字节一致"（SC-001）在工程上可达成；6 位小数对 [0,1] 得分足够。

## 决策 7：与 promo 执行器保持各自实现

**决策**: visual loop 与 promo loop 编排形态相似（门禁/幂等/对账），但本期**不**提炼
公共编排框架，各自实现。

**理由**: 两个实例不足以确定正确的抽象边界（预算语义、状态机细节、物料形态都有差异）；
过早抽象的风险大于重复（YAGNI，宪章评审要求）。第三个 Agent（声音/剪辑）接入时若形态
稳定再提炼。重复部分以评审备注显式声明。
